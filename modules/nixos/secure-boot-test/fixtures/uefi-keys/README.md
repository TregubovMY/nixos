# Test-only UEFI Secure Boot keys — NOT secrets

The `.key`/`.pem`/`.auth` files under `keys/{PK,KEK,db,dbx}/` in this
directory are lanzaboote's own **published, throwaway** test PKI, vendored
byte-identical from upstream `nix-community/lanzaboote` (rev
`7c9a54a7f87b4539ddbd8bda09a8a5f5f9361aa9`, matching this repo's
`flake.lock`) — not generated by or specific to this repository, and not
used anywhere near a real machine.

**Why these are safe to commit despite containing `-----BEGIN PRIVATE
KEY-----` blocks**, per `CLAUDE.md`'s hard rule against committing secret
material: they secure nothing. They exist only to let
`modules/nixos/secure-boot-test/systemd-initrd.nix` enroll a self-signed
Secure Boot chain into a throwaway QEMU VM's simulated UEFI firmware
(OVMF) during `nix flake check -L`. They are never used by, referenced
from, or reachable by `modules/nixos/secure-boot.nix`'s real `pkiBundle`
path (`/var/lib/sbctl`) — that path is populated only by a real `sbctl
create-keys` run on real hardware, at real-install time, which this repo
never does. Same public source, same public keys as anyone who clones
`nix-community/lanzaboote` and runs its test suite.

**Known cert expiry** (checked via `openssl x509 -enddate`, 2026-08-10):
`PK`/`KEK`/`db` expire 2027-11-23; `dbx.pem` already expired 2024-10-22.
The test currently passes regardless — UEFI `db` matching in this VM test
isn't date-driven, and `dbx` isn't enrolled by `common/image.nix`. Not
currently a defect, but another reason to re-vendor this whole directory
(not patch expiry dates in place) whenever the `lanzaboote` flake input is
bumped — see `flake.nix`'s own note next to `inputs.lanzaboote`.
