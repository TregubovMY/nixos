# CLAUDE.md — как работать с этим репозиторием

Это NixOS-конфигурация (flake), описывающая переносимую систему:
disko-разметка диска + LUKS, systemd-boot, Hyprland-десктоп, home-manager
dotfiles, секреты через sops-nix. Полное описание — в `system-plan.md`.

## Главное правило: никогда не применять изменения напрямую на хост-системе

Агент **не запускает** `nixos-rebuild switch` на реальной машине без явной
просьбы пользователя. Весь цикл разработки и самопроверки идёт через
виртуальную машину или dry-run сборку. Причина: ошибка в конфиге диска/boot
может сделать систему незагружаемой — такого риска в цикле правок быть не должно.

## Цикл разработки (от дешёвого к дорогому)

Всегда идти по этим шагам по порядку, не пропуская более дешёвые проверки:

1. **Синтаксис и eval** (секунды):
   ```bash
   nix flake check
   ```
   Ловит синтаксические ошибки Nix и несовместимость опций модулей без
   реальной сборки. Гонять после **каждого** изменения `.nix`-файла.

2. **Dry-build** (секунды–десятки секунд):
   ```bash
   nixos-rebuild dry-build --flake .#<hostname>
   ```
   Проверяет, что деривация вообще способна собраться (какие пакеты будут
   собираться/скачиваться), не строя итоговую систему.

3. **Сборка VM-образа** (минута-две):
   ```bash
   nixos-rebuild build-vm --flake .#<hostname>
   ./result/bin/run-*-vm
   ```
   Даёт полноценную загружаемую виртуалку с этим конфигом. Использовать
   для проверки, что графическое окружение/сервисы реально поднимаются.
   Агент не может "посмотреть глазами" на Hyprland — визуальную часть
   подтверждает пользователь. Агент подтверждает: VM собралась и
   загрузилась без паники ядра / без failed systemd unit-ов.

4. **Проверка systemd-юнитов внутри VM** (если нужно глубже):
   ```bash
   # внутри VM, через serial console или ssh, если пробросить порт
   systemctl --failed
   ```
   Пустой вывод = все сервисы поднялись штатно.

5. **Тест разметки диска (disko + LUKS)** — только на виртуальном диске,
   никогда не на реальном блочном устройстве без явного подтверждения
   пользователя:
   ```bash
   qemu-img create -f qcow2 /tmp/test-disk.qcow2 20G
   # прогнать disko против виртуального диска внутри тестовой VM
   ```

6. **Полная установка** (`nixos-install`) — только по явной просьбе
   пользователя и только когда шаги 1–5 прошли чисто.

## Дисковый бюджет при разработке

На машине разработки может быть мало свободного места и нет запасного
диска для тестов — все проверки идут на том же диске, где живёт текущая
рабочая система. `dry-build`/`build-vm` саму хост-систему не меняют (не
трогают загрузчик, не переключают конфиг — это делает только
`nixos-rebuild switch`, которую агент не запускает без явной просьбы, см.
главное правило). Но они могут **забить диск**, а от нехватки места
текущая система может начать сбоить сама по себе (ENOSPC у случайного
процесса) — это и есть основной риск на шагах 3 и 5, и относиться к нему
нужно как к угрозе самой системе, а не просто к неудобству:

- **Жёсткий порог: не начинать тяжёлую сборку (шаг 3, 5), если после неё
  свободного места останется меньше ~5GB** (оценивать по факту известного
  размера предыдущих сборок/образов, не гадать). Если по прикидке грозит
  уйти ниже порога — сначала `nix-collect-garbage -d` (или `nix store gc`);
  если и после очистки места впритык — остановиться и спросить
  пользователя, а не пробовать "а вдруг поместится".
- После каждой тяжёлой сборки — чистить за собой, не копить старые
  generations/store-пути между итерациями.
- Для disko-теста — qcow2-образ разумного размера (например, 8G, не 20G):
  формат sparse, реально расходуется место только под фактически
  записанные данные (таблица разделов + LUKS-заголовок), раздувать образ
  без нужды незачем.
- Если для проверки нужен полный десктоп-набор (Hyprland + Chrome +
  RubyMine + VSCode и т.п.) — это может занять заметно места. На ранних
  итерациях проверять базовые модули (диск/boot/сервисы) отдельно от
  полного пакетного набора, не тянуть всё сразу.

## Makefile-шорткаты (если есть/нужно завести)

```makefile
check:      nix flake check
dry:        nixos-rebuild dry-build --flake .#$(HOST)
vm:         nixos-rebuild build-vm --flake .#$(HOST) && ./result/bin/run-*-vm
disko-test: # тест разметки на qcow2-образе
```
Агент может сам добавлять/расширять таргеты — держать их простыми и
именованными очевидно.

## Работа с секретами — жёсткие ограничения

- **Никогда** не выводить, не логировать и не коммитить расшифрованное
  содержимое `secrets/secrets.yaml` — даже во временные файлы, даже в
  комментарии, даже в debug-вывод команд.
- Файл `secrets/secrets.yaml` в репозитории **всегда зашифрован** — если
  агент видит там читаемый plaintext, это баг, который нужно исправить
  до коммита (пересобрать через `sops`), а не считать нормальным состоянием.
- Новые секреты добавлять только через `sops secrets/secrets.yaml`
  (открывает файл на редактирование в расшифрованном виде во временном
  редакторе, сохраняет обратно зашифрованным) — не редактировать файл
  напрямую текстовым редактором/`str_replace`.
- `.sops.yaml` — публичный файл, его редактировать можно свободно, он не
  содержит секретов, только публичные age/GPG ключи получателей.
- Если пользователь просит "добавить токен/пароль в конфиг" — секрет идёт
  в `secrets.yaml` через `sops`, а `.nix`-модуль ссылается на
  `config.sops.secrets.<name>.path`, не на само значение.

## Структура модулей — куда класть новый код

- Новый **системный** сервис/настройка (не зависит от пользователя) →
  `modules/nixos/<тема>.nix`, подключить в `hosts/<host>/configuration.nix`.
- Новый **пользовательский** пакет/dotfile (тема, шелл, редактор) →
  `modules/home/<тема>.nix`, подключить в home-manager конфиг пользователя.
- Новый **хост** (другая машина) → копировать `hosts/laptop/` в
  `hosts/<новое-имя>/`, поправить `disk-config.nix` под конкретный диск
  (`/dev/nvme0n1` vs `/dev/sda` и т.п.) и `hardware-configuration.nix`
  сгенерировать заново через `nixos-generate-config` на целевой машине.
- Общий, переиспользуемый софт-стек (Hyprland, tmux, neovim) не должен
  зависеть от хост-специфичных деталей — так репозиторий остаётся
  переносимым между машинами и людьми.

## Комментарии и документация в коде

Для этого репозитория — намеренное исключение из общего правила "код без
комментариев, если это не объясняет WHY". Здесь наоборот: каждый
нетривиальный `.nix`-модуль, скрипт или workaround должен сопровождаться
комментарием, достаточно подробным, чтобы разобраться в нём через
полгода, уже не помня контекста. Не "что делает код" (это обычно и так
ясно из имён/структуры), а **почему выбран именно этот вариант**: ссылка
на документацию/issue/PR/обсуждение, если решение оттуда, нюансы
конкретной версии, причина, по которой отвергнуты более очевидные
альтернативы. Особенно важно для:

- сторонних дериваций пакетов (см. также "Правила для пакетов" ниже —
  источник бинарника и версия обязательны);
- воркэраундов вокруг багов/несовместимостей версий;
- нестандартных архитектурных решений (например, почему песочница
  агентов устроена именно так, а не иначе — см. `system-plan.md`, п.9).

`README.md` поддерживать в актуальном состоянии как входную точку для
человека (не для агента) — что это за репозиторий, как развернуть, куда
смотреть за деталями (структура — `system-plan.md` п.3), плюс практические
инструкции без которых не разобраться с ходу (например, как подключить
IDE к проекту, запущенному в песочнице агента — `system-plan.md` п.9.5).

## Правила для пакетов

- Проверять доступность пакета в nixpkgs **перед** тем как писать свою
  derivation: `nix search nixpkgs <имя>` или https://search.nixos.org.
- Unfree-пакеты (rubymine, google-chrome, vscode, postman) требуют
  `nixpkgs.config.allowUnfree = true` — уже должно быть включено в
  `flake.nix`/`configuration.nix`, не дублировать в каждом модуле.
- Если пакета нет в nixpkgs (например, Throne/NekoBox) — оборачивать
  через отдельный `.nix` в `modules/nixos/packages/<имя>.nix`, документируя
  источник бинарника и его версию прямо в комментарии над derivation —
  чтобы через полгода было понятно, зачем и откуда это взялось.

## Искать готовые решения, а не изобретать свои

Перед тем как писать конфиг/модуль с нуля (особенно для сложных стеков —
Hyprland, waybar, kitty, zsh-плагины, конфиги LSP и т.п.) — сначала искать
в интернете актуальное, проверенное сообществом решение: официальную
документацию, готовые dotfiles/nix-модули, обсуждения проблем с конкретной
версией. При необходимости скачать/открыть документацию, чтобы свериться
с текущим API/синтаксисом, а не полагаться на память о том, как это
работало раньше — конфиг-синтаксис (особенно у Hyprland) меняется между
версиями. Собственная derivation/конфиг с нуля — крайний случай, когда
готового решения не нашлось, а не первый вариант по умолчанию.

## Git-гигиена

- Коммитить осмысленными пачками: один логический модуль/фича — один
  коммит, не смешивать "добавил Hyprland-конфиг" и "поправил disko" в
  одном коммите.
- `flake.lock` коммитить всегда вместе с изменениями, которые его вызвали
  (`nix flake update <input>`) — отдельным коммитом, не смешивать с
  правками конфигов.
- Перед коммитом прогонять минимум шаг 1 (`nix flake check`) — коммит с
  синтаксической ошибкой недопустим.

## Если что-то не собирается

- Читать ошибку Nix до конца — она обычно указывает конкретный файл и
  строку, но причина может быть в модуле, который импортируется этим
  файлом (следовать по цепочке `imports`).
- Не гадать и не "чинить одной правкой на удачу" при сложных ошибках —
  сначала воспроизвести минимальный случай (закомментировать половину
  модулей, найти виновника бисекцией), затем чинить.
- Если ошибка похожа на несовместимость версий (например, Hyprland 0.55
  vs старый конфиг-синтаксис) — свериться с CHANGELOG апстрима перед тем
  как менять конфиг вслепую.
