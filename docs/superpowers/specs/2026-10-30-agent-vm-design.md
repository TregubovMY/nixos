# agent-vm: microVM для агентов с Docker (design)

Статус: реализовано (2026-10-30), НЕ запускалось: `nix flake check --no-build`
и `nix build --dry-run` на toplevel проходят, гость (`microvm.declaredRunner`)
собирается, конфиг фильтра проходит `sing-box check`, поведение фильтра
проверено на фейковом SOCKS-сервере. Живой запуск VM и `agent-vm test` —
за пользователем после `nixos-rebuild switch` (меняется файрвол хоста).
Код: `modules/nixos/agent-vm.nix`, `bin/agent-vm`.

## Зачем

`agent-sandbox` (rootless podman, `system-plan.md` §9) не даёт агенту Docker:
сокет хоста — root-эквивалент (отвергнуто), вложенный podman не проверен
(`TODO.md`, `/tmp/nested-podman-check.sh`). Исследование аналогов
(`docs/REFERENCE.md`, «Аналоги `agent-sandbox`») показало, что готовой замены
нет, а microVM были «вне модели угроз §9.1». Модель угроз меняется: пользователь
хочет дать агенту Docker и **не переживать, если VM взломают**. Поэтому
добавляется второй режим рядом с песочницей, а не вместо неё.

## Требования пользователя (2026-10-30)

1. Агент работает с Docker/контейнерами, в том числе `--privileged`.
2. Работа идёт не в ОС хоста: взлом = потеря VM, не хоста.
3. Нет ssh к чему-либо, нет доступа во внутренние сети (LAN, домашний
   OpenVPN, podman0, libvirt) — только наружу в интернет.
4. Claude/kandev удобно открывать в браузере.

Факты о хосте, на которые опирается дизайн (проверено 2026-10-30):
`/dev/kvm` есть, железо физическое, 24 потока, 130 ГБ свободно; Throne
работает в TUN-режиме, часть трафика идёт напрямую по доменным правилам,
часть через прокси, «не всё открывается без прокси»; mixed-inbound Throne
слушает **только `127.0.0.1:2080`**; на домашнем ПК добавится OpenVPN.

## Архитектура

```
браузер хоста ─ 127.0.0.1:P ─(хост инициирует)─▶ microVM 10.200.0.2
                                                   claude / kandev / ttyd / docker
                                                   проект: клон ВНУТРИ VM
microVM ──► 10.200.0.1:3128 (фильтрующий прокси на хосте) ──► Throne :2080 ──► интернет
            все остальное из VM: drop
```

- **microvm.nix** (`github:astro/microvm.nix`), гипервизор qemu с KVM
  (самый совместимый с virtiofs; cloud-hypervisor — возможная оптимизация).
  Почему microVM, а не контейнер: у гостя своё ядро, Docker внутри работает
  штатно, побег требует эксплойта гипервизора, а не ядра.
- **`/nix/store` хоста — virtiofs, только чтение**: сохраняется идея
  «rootfs из `/nix/store` без образов».
- **Постоянный том** (`microvm.volumes`, ext4-образ) под `/var/lib/docker` и
  `/home/agent`. Пересоздаваемый: `agent-vm reset` стирает том.
- **Проекты — virtiofs по тем же путям, что на хосте** (изменено 2026-10-30
  по просьбе пользователя; сначала был «клон внутри VM»). Одна VM, список
  `agentVm.mounts`, пользователь VM = пользователь хоста (имя, uid, `$HOME`),
  аккаунты Claude — только перечисленные + `shared/` (общие сессии). Цена:
  `rw`-монтирование — канал на хост (хуки git, `.envrc`, `mise.toml`,
  скрипты `package.json`): VM защищает систему и внутреннюю сеть, но не
  файлы проекта. Смягчение — `ro`, ревью `git diff` и хуков; идея на потом —
  монтировать `.git/hooks` поверх только для чтения.
- **Сеть**: отдельный мост `agentbr0` (10.200.0.0/24), статические адреса
  (без DHCP/DNS на хосте), `net.ipv4.ip_forward` для этого моста **не
  включается** — маршрутизации из VM нет вообще.

### Файрвол хоста (nftables, список разрешённого)

- `input`: из `agentbr0` разрешено только `tcp dport 3128` к `10.200.0.1`.
  Всё остальное, включая ping и DNS к хосту, — drop.
- `forward`: из/в `agentbr0` — drop (кроме established для проброса порта
  браузера).
- `output` хоста → VM: разрешён (хост инициирует соединения к
  `10.200.0.2:P`; ответы — conntrack established).
- Не перечисляем запрещаемые подсети/интерфейсы (`tun0`, `throne-tun`,
  `172.22.0.0/23`) — не нужно: forwarding у VM нет, единственный выход —
  прокси. Поэтому домашний OpenVPN ничего не ломает.

### Выход наружу: прокси

VM видит только `http://10.200.0.1:3128`. В госте: `HTTP(S)_PROXY`/`NO_PROXY`
в окружении, `docker daemon` (`proxies` в `daemon.json`), nix/apt/git/npm
берут из env. Контейнеры внутри VM получают прокси через `~/.docker/config.json`
(`proxies.default`). Сырой TCP/UDP наружу не работает — принятая цена.

Прокси на хосте — отдельный процесс на `10.200.0.1:3128`, цепочкой на Throne
(`127.0.0.1:2080`): доменные правила Throne (напрямую/через прокси) работают
как у пользователя.

## Где режутся приватные адреса (решено: вариант 2, второй sing-box)

Throne для «direct» с радостью соединится с `172.22.x`, `192.168.x`, `10.x`,
OpenVPN-подсетями, поэтому фильтр стоит перед ним: `agent-vm-proxy`
(sing-box из nixpkgs) на `10.200.0.1:3128` → SOCKS `127.0.0.1:2080` (Throne).

Проверено на фейковом SOCKS-сервере (2026-10-30, sing-box 1.14.3): после
правила `action = resolve` в SOCKS-upstream уходит **уже проверенный IPv4-адрес
(ATYP=1), а не имя**. Значит DNS-rebinding невозможен: адрес, прошедший
проверку, и есть тот, к которому подключится Throne. Отклонены (не дошли
до upstream): `172.22.1.1`, `192.168.122.1`, `10.88.0.1`, `100.64.1.1`,
`198.18.0.5`, `169.254.169.254`, `172.22.1.1.nip.io`, `localhost.localtest.me`,
CONNECT на IP-литерал. Публичные (`1.1.1.1`, `example.com`) прошли.
Варианты 1 (inbound в Throne) и 3 (Squid/tinyproxy) отвергнуты: первый
зависит от возможностей Throne, третий передаёт Throne **имя** и оставляет
второй резолв (rebinding).

Цена: Throne видит IP-литералы, поэтому его правила **по доменам** срабатывают
только если на его inbound включён sniff (TLS SNI / HTTP Host). Приёмочный
тест ниже («домен, доступный только через прокси Throne») это проверяет;
если не работает — включить sniff у mixed-inbound Throne.

## Приёмочные тесты (из VM)

- `curl https://example.com` и `docker pull alpine` — работают (в том числе
  домен, который открывается только через прокси Throne — именно он
  проверяет sniff, см. выше).
- `curl http://172.22.1.1`, `curl http://10.200.0.1:22`, `curl 127.0.0.1` хоста,
  `curl http://172.22.1.1.nip.io` (rebinding на LAN), `curl http://192.168.122.1` —
  все падают.
- `ping 1.1.1.1`, прямой `nc 1.1.1.1 443` без прокси — не работают.
- Внутри VM `docker run --privileged` и `docker run alpine wget <LAN-ip>` —
  второе падает.
- `ip route` / `ss` в госте не показывают ничего, что ведёт мимо прокси.
- С хоста: `curl 127.0.0.1:P` открывает kandev/ttyd.

Все пункты, кроме последнего, автоматизирует `agent-vm test`.

## Браузерный доступ

- Хост пробрасывает `127.0.0.1:P → 10.200.0.2:P` (systemd socket proxy или
  `socat`), только loopback.
- kandev — уже веб-сервис; для Claude в браузере `ttyd` (терминал) или
  `code-server`. Порты фиксированы в конфиге VM.
- Контент из VM недоверенный: открывать в отдельном профиле браузера,
  без пользовательских сессий (XSS/CSRF к локальным сервисам хоста).

## Секреты (остаточный риск)

Всё, что лежит в VM, при взломе считается скомпрометированным:

- git — deploy-key/fine-grained token на один репозиторий;
- Claude — отдельный аккаунт или с лимитами; OAuth-токен живёт в VM;
- ssh-agent, `~/.ssh`, Bitwarden, `SSH_AUTH_SOCK` в VM **не пробрасываются**;
- приватный docker-registry — отдельный read-only токен.
  Секреты не в `.nix` и не в git (`CLAUDE.md`, «Работа с секретами»).

## Интерфейс

`agent-vm up|down|reset|shell|status` (по образцу `bin/agent-sandbox`),
`up` печатает адреса для браузера. Режим дополняет `agent-sandbox`: быстрые
задачи с GUI — там, задачи с Docker — здесь.

## Не входит

GUI/Playwright в VM; подмена секретов на прокси; egress-allowlist по доменам
(возможное расширение прокси, см. `TODO.md`); перенос на отдельную машину
(схема не меняется, меняется только мост).
